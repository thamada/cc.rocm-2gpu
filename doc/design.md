# 設計仕様書

> **注意**: 本ドキュメントは設計仕様書です。変更履歴は `ChangeLog.md` を参照。以下は**現在の**システム設計である。

## 概要

2 枚の GPU について、次の転送帯域を 1 回の実行で測る ROCm/HIP ベンチマークである。

1. GPU 間の単方向（A→B と B→A）
2. GPU 間の双方向（上記 2 本を同時に流した合計）
3. Host↔VRAM の書き込み（Host→VRAM）と読み出し（VRAM→Host）。各方向で、GPU 単独と 2 GPU 同時の両方

帯域の単位は GB/s = 10^9 バイト/秒である。GiB/s（2^30）ではない。双方向と「同時合計」は、同じ時間窓に流れた両方向（または両 GPU）のバイト数を足して、その窓の時間で割った値である。

ピアアクセスが両方向で使えるときは `hipMemcpyPeerAsync` で VRAM から VRAM へ直接コピーする。使えないときは、ピン留めホストメモリを挟んだダブルバッファで GPU→ホスト→GPU を測る。このマシンの Radeon 同士は後者である。

転送が終わった最大サイズのバッファは、送信側と同じ 32bit パターンと照合する。不一致があれば終了コード 1 になる。

## ビルド・実行

既定ゴールは `run` である。`run` は `build` のあと `./p2p-bw` を起動する。

```bash
make run
make run GPU_A=0 GPU_B=1 MAX_MB=16384 ITERS=0
make detect-gpu-arch
make build
make clean
```

`GPU_ARCH` は `rocminfo` の最初の `gfx*` 名から取る。検出できないときは `make GPU_ARCH=gfx1201 run` のように渡す。`hipcc` には、ホストの `g++` が見つけた GCC の `--gcc-install-dir` を付ける。

| 変数 | 既定値 | 説明 |
|------|--------|------|
| `GPU_A` | 0 | 一方の GPU 番号。実行ファイルの第 1 引数 |
| `GPU_B` | 1 | もう一方の GPU 番号。第 2 引数 |
| `MAX_MB` | 16384 | 1 バッファの上限（MiB）。第 3 引数。空き VRAM に収まらなければ縮小する |
| `ITERS` | 0 | 反復回数。第 4 引数。0 はサイズごとに自動 |
| `ROCM` | `/opt/rocm` | ROCm のプレフィックス |
| `HIPCC` | `$(ROCM)/bin/hipcc` | コンパイラ |
| `GPU_ARCH` | `rocminfo` から検出 | `--offload-arch` |

ホスト経由の GPU 間転送だけ、環境変数 `P2P_CHUNK_MB` でチャンクサイズを変える。有効範囲は 1..256、既定は 8。範囲外は既定のままである。

```bash
P2P_CHUNK_MB=8 ./p2p-bw 0 1 16384 0
```

`make clean` は `p2p-bw` だけを消す。

## 実行ファイル

```
./p2p-bw [gpu_a] [gpu_b] [max_mb] [iters]
```

引数を省略したときの既定は `0 1 16384 0` である。`gpu_a` と `gpu_b` は、デバイス数の範囲内で、互いに異なる番号でなければならない。GPU が 2 枚未満、番号が不正、使える VRAM が 4 KiB 未満のときは終了コード 1 で戻る。`max_mb` が 0 のときは 1 として扱う。

## 計測の順序

1. 全デバイスの名前、アーキテクチャ、CU 数、クロック、VRAM、PCI バス ID を表示する。
2. 指定した 2 台のリンク種別と hop 数、ピアアクセスの可否、`hipDevP2PAttrPerformanceRank` を表示する。リンク種別が `0xFFFFFFFF` のときは「直接リンクなし」と出す。
3. 空き VRAM から最大サイズを決め、各 GPU に送信用と受信用の 2 面を確保する。
4. GPU 間を単方向 2 本、続いて双方向で測る。
5. 最大サイズの受信バッファをパターン照合する。
6. 送信用 VRAM を Host↔VRAM に転用する。書き込みを全サイズ測ってから、読み出しを全サイズ測る。各サイズは単独 A、単独 B、同時の順である。
7. サイズ横断のピークをサマリに出す。

サイズ列は 4 KiB から 4 倍ずつ増やし、最後をちょうど最大サイズにする。4 KiB 未満はコピーエンジンの起動コストが支配的なので測らない。

## バッファサイズ

`MAX_MB` と実行ファイル第 3 引数の既定は **16384 MiB（16 GiB）** で、1 面あたりの要求サイズである。各 GPU に送信と受信の **2 面** が要るので、VRAM だけを見ると 1 GPU あたり最大で **32768 MiB（32 GiB）** 相当の確保を試みる。Host↔VRAM 用のピン留めホストバッファも、採用した `nbytes` と同じ大きさである。

2 台の空き VRAM の小さい方から 512 MiB を引き、その半分が 1 面の上限である。空きが 512 MiB 以下のときは空きの半分を予算にする。16384 MiB の要求がこの上限を超えるときは、その旨を表示して上限に縮小する。256 バイト未満の端数は切り捨て、パターン照合のワード境界とコピーのアライメントを揃える。

## GPU 間の経路

`hipDeviceCanAccessPeer` が両方向で真なら、ピアを有効にして `hipMemcpyPeerAsync` を使う。すでに有効なら成功とみなす。有効化に失敗してもプロセスは止めず、ホスト経由へ切り替える。`canAccessPeer` が真でも実コピーが失敗する環境があるため、ピア経路では 1 MiB の `hipMemcpyPeer` を試し、失敗したら同じホスト経由に落とす。

ピアが使えないときは、ドライバの直列中継に任せない。方向ごとにピン留めホストを 2 枚用意し、チャンク単位で重ねる。

- スロット 0 へ、送信 VRAM から最初のチャンクを読む。
- そのチャンクを宛先 VRAM へ書いているあいだに、スロット 1 へ次のチャンクを読む。
- 同じスロットを再利用する前に、宛先が読み終わったイベントを待つ。

1 枚のバッファで全部を送ってから次へ進むと、所要時間は往路と復路の和になり、実効帯域はおよそ半分になる。2 枚に分けると、大きいサイズの帯域は遅い方の片道に近づく。チャンクが転送サイズ以上のときは重ねる相手が無いので、結果は往復の直列転送になる。小さいサイズの数字が頭打ちなのはそのためである。

双方向では A→B 用パイプと B→A 用パイプを同時に積む。ホストバッファはパイプごとに別である。帯域は両方向の和であり、片方向の速度ではない。

コピーは送信側デバイスのストリームに載せる。計測窓の開始は送信ストリーム、終了は宛先の最後の書き込みを送信ストリームが待ったあとである。宛先のイベントを、別デバイスの `hipEventElapsedTime` に直接渡さない。

## Host↔VRAM

ホスト側は `hipHostMalloc` でピン留めする。ページング可能な `malloc` は実行時コピーが入り、リンクそのものの速度にならない。GPU ごとにホスト領域を分ける。同じページを両 GPU が叩くと、リンクではなくホストメモリ上の競合を測る。

書き込みと読み出しは同時には流さない。読み出しの前に書き込みが一巡しているので、読むデータは VRAM 上にある。VRAM 側は GPU 間計測の送信用バッファを再利用する。ここでは新たに `hipMalloc` しない。

| 列 | 意味 |
|----|------|
| GPU 単独 | 相手 GPU は転送していない。その GPU の片道の目安 |
| 同時 GPU | 2 GPU が並行しているときの、その GPU 自身の転送時間から出した帯域。相手の完了は待たない |
| 同時合計 | 両 GPU が終わるまでの時間で、両 GPU の転送量の和を割ったスループット |

同時合計は、同時 A と同時 B の和とは一致しない。遅い方に揃うまでの待ちが分母に入る。壁時計は GPU A のストリーム上で、GPU B の完了イベントを待ってから記録する。B の経過は B のイベント対だけで取る。

## 時間と反復

ホスト側の時計は使わない。各ストリームに `hipEvent` を置き、`hipEventElapsedTime` で GPU 側の経過を取る。イベントを記録したデバイスと、経過を問い合わせるときのカレントデバイスは揃える。

本計測の前に 3 回ウォームアップし、初回の割り当てとエンジン起動を窓から外す。ウォームアップのあとストリームを同期してから開始イベントを記録する。

`ITERS` が 1 以上なら全サイズでその回数を使う。0 のときは、そのサイズでおよそ 2 GiB 運ぶ回数にする。小さいサイズはイベントの分解能に負けるので下限を上げる。64 KiB 以下は 400 以上、1 MiB 以下は 100 以上、それより大きいサイズは 8 以上。上限は 500 である。

帯域は `(bytes × iters × directions) / 窓の時間` である。`directions` は単方向と単独が 1、GPU 間の双方向と Host の同時合計が 2 である。表の「1回転送」は、窓の時間を反復回数で割った 1 回分の所要時間である。

## 検証

パターンはインデックスとシードから一意に再現する。期待値の別バッファは持たない。式はホストとデバイスで同じである。

| 用途 | シード |
|------|--------|
| GPU A の GPU 間送信 | `0xA11A0001` |
| GPU B の GPU 間送信 | `0xB22B0002` |
| Host↔VRAM の GPU A | `0xC33C1001` |
| Host↔VRAM の GPU B | `0xD44D2002` |

GPU 間では送信バッファを計測中に書き換えない。最後の最大サイズ転送のあと、受信側をデバイス上で全ワード照合する。不一致は原子加算で数える。

Host↔VRAM では、書き込み後の VRAM をデバイス上で照合し、読み出し後のホストメモリを CPU で全ワード照合する（既定の上限は 16 GiB）。シードを GPU 間と変えてあるので、バッファの取り違えは不一致になる。各サイズの最後の同時転送がバッファ全体を覆うので、最大サイズの照合で足りる。

## 出力

セクションは次の順で出る。

- デバイス一覧
- リンクとピアアクセス、採用した計測方式
- 設定（GPU 番号、最大サイズ、反復の選び方、チャンク、帯域の定義）
- 単方向 2 本と双方向の表（サイズ、反復、1回転送、帯域）
- GPU 間の検証
- Host→VRAM と VRAM→Host の表（サイズ、反復、各 GPU の単独、同時の各 GPU、同時合計）
- Host↔VRAM の検証
- サマリ（方式、理論ピークの基準、各ピークとそれが現れたサイズ、理論ピークに対する実行効率、検証の合否）

理論ピークは、GPU からルートポートまで辿った各ホップの交渉済み速度・幅のうち、片方向ペイロードが最も小さいもの（GB/s = 10^9 バイト/秒）である。デバイス直結の `current_link_speed` だけでは決めない。スイッチの下流が 32 GT/s でも、ルートポートが 8 GT/s x16 なら上限はそちらになる。符号化は Gen1/2 が 8b/10b、Gen3–5 が 128b/130b、Gen6 が FLIT の 242/256。実行効率は実測 ÷ この理論ピーク。

| 行 | 理論ピーク |
|----|------------|
| Host の単独 | その GPU の経路で最も遅いホップ |
| Host の同時合計 | 両 GPU の最遅ホップの和 |
| GPU 間の片方向 | 両経路の遅い方 |
| GPU 間の双方向合計 | 片方向の理論ピークの 2 倍（全二重） |

xGMI のとき GPU 間にはこの PCIe 上限を置かず、「理論ピーク不明」と出す。リンク情報を読めない行も同様である。

## 終了コード

パターン照合がすべて一致すれば 0、1 ワードでも違えば 1。HIP API が失敗したときは呼び出し地点を残して直ちに終了する。ピアの有効化失敗と、リンク情報の取得失敗は、計測方式の切り替えに使うので、この即時終了には含めない。
